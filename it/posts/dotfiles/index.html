I miei Dotfiles: un Ambiente di Sviluppo per il DevOps

Come gestisco i miei dotfiles con chezmoi, la toolchain su cui mi sono assestato, e come herdr è diventato la casa dei miei coding agent.

Gestire un ambiente di sviluppo su più macchine è un problema risolto — se si è disposti a investire un po’ di tempo all’inizio. Questo post spiega come gestisco i miei dotfiles usando chezmoi, la toolchain su cui mi sono assestato, e come ho sostituito il mio terminal multiplexer con herdr, un multiplexer costruito attorno ai coding agent.

Perché chezmoi?#

I gestori di dotfiles esistono in molte varianti: repository git bare, GNU Stow, script shell personalizzati. Ho scelto chezmoi per alcuni motivi:

  • Templating: un singolo dot_gitconfig.tmpl può rendere valori diversi per macchina (email di lavoro vs. email personale) usando i template Go. I valori vivono in ~/.config/chezmoi/chezmoi.toml, fuori dal repo, con dei fallback ragionevoli scritti direttamente nel template.
  • Niente symlink: chezmoi copia i file nella destinazione, quindi non basta un rm per rompere tutto.
  • Supporto nativo ai segreti: si integra con i password manager, la cifratura age e le variabili d’ambiente.
  • Binario singolo: niente Ruby, niente Python, nessuna dipendenza di sistema — solo un binario gestito da mise.

Bootstrap di una nuova macchina#

Tutto parte da un unico script — un gist — che si occupa di:

  • Installare i pacchetti di sistema base
  • Configurare Docker
  • Installare FiraCode Nerd Font
  • Installare mise
  • Impostare Fish come shell predefinita

Poi un riavvio, e:

mise x chezmoi -- chezmoi init --apply thewalterman
mise install
nvim   # lazy.nvim installa i plugin

Da zero a produttivo con una manciata di comandi.

La toolchain#

mise: uno strumento per governarli tutti#

Invece di gestire Node con nvm, Python con pyenv, e così via, uso mise. Un singolo config.toml dichiara tutto:

  • Kubernetes/DevOps: kubectl, helm, k9s, flux2, k3d
  • Editor: neovim
  • Produttività: lazygit, lazydocker, yazi, herdr
  • Shell: starship, fzf, zoxide, navi, eza, bat, fd, ripgrep

Tutto punta a latest. Ho smesso di pinnare il tooling personale: un task mise run full-upgrade (mise self-update -y && mise upgrade) aggiorna l’intera macchina in un colpo. Lo stesso file imposta anche EDITOR/KUBE_EDITOR su nvim.

Fish shell + starship#

Fish offre autosuggestions ed evidenziazione della sintassi out of the box. Faccio largo uso di abbr (abbreviazioni) invece degli alias — si espandono inline, così vedi sempre il comando completo prima che venga eseguito.

Gli alias veri e propri sono riservati alle sostituzioni secche: cat → bat -pp, ls → eza --icons, grep → rg -i. La catena di init in fondo a config.fish è mise → starship → fzf → zoxide (che prende il posto di cd) → navi widget. Completano il quadro alcune funzioni custom: y (yazi che cambia la directory della shell all’uscita), fcd (picker di directory con fzf e anteprima eza), fkube e fssh.

Per il prompt uso starship, configurato interamente tramite dot_config/starship.toml. Funziona identico in Fish e Bash, e uso lo slot del prompt di destra per mostrare il contesto Kubernetes corrente.

Neovim (LazyVim)#

Uso LazyVim come base e aggiungo un piccolo insieme di plugin:

  • bufferline — navigazione tra i buffer simile alle tab con Shift+frecce
  • smart-splits — navigazione tra i pannelli con Alt+frecce
  • nvim-spider — movimenti w/b/e più intelligenti che rispettano camelCase e underscore
  • nvim-numbertoggle — numeri relativi in normal mode, assoluti in insert mode
  • herdr-nvim — la metà Neovim dell’integrazione con herdr (più sotto)

navi#

navi è un tool di cheatsheet interattivo — premi una scorciatoia, cerchi un cheat con fuzzy search, riempi i placeholder, e ti mette il comando finito sul prompt invece di eseguirlo alla cieca. È agganciato a Fish tramite navi widget fish, sul solito Ctrl+G.

I cheatsheet vivono in dot_config/navi/cheats/ e coprono i comandi che altrimenti dovrei cercare ogni volta: kubectl (logs, exec, describe, rollout restart, decodifica dei secret), helm (values, manifest, history, rollback, diff), docker (volumi, network, prune, compose) e flux (reconcile, suspend/resume, log degli errori) — ognuno chiede namespace, pod o release tramite una query kubectl/helm dal vivo invece di un esempio fisso.

herdr: la casa degli agent#

herdr è un terminal multiplexer pensato per far girare coding agent. Fa quello che fanno tmux e Zellij — server persistente, detach/attach, workspace, tab, split — ma in più sa quali pannelli stanno eseguendo un agent (Claude Code, Codex, Gemini, pi, opencode e una lunga lista di altri) e in che stato si trova ciascuno: al lavoro, bloccato in attesa di input, finito, inattivo. Con due o tre sessioni di Claude aperte su repo diversi, la domanda non è mai “dov’è la mia shell?”, ma “quale agent mi sta aspettando?”.

Si installa tramite mise come tutto il resto, e si configura in dot_config/herdr/config.toml.

La sidebar#

La sidebar a sinistra è il cuore dell’interfaccia. Ha due sezioni:

  • Spaces (workspace) — uno per progetto, ognuno con un’icona di stato, il nome del workspace e sotto il branch git e lo stato del repo.
  • Agents — tutti gli agent di tutti i workspace, raggruppati per space (agent_panel_sort = "spaces"), con status_indicators = "symbols" così bloccato/al lavoro/finito sono glifi distinti invece di pallini colorati che a colpo d’occhio non distinguo.

Per Claude sovrascrivo il layout delle righe per mostrare anche il titolo del terminale — Claude Code ci scrive un breve riassunto del task in corso, quindi la sidebar diventa di fatto un elenco live di cosa sta facendo ogni agent.

Notifiche#

Quando un agent in un workspace in background finisce o ha bisogno di attenzione, herdr manda una notifica. Ho impostato delivery = "system", quindi va direttamente al servizio di notifiche del desktop — posso essere nel browser e sapere comunque che Claude aspetta una conferma di permessi.

Scorciatoie#

Il prefisso è il Ctrl+b di default, così la muscle memory di tmux resta valida. In aggiunta:

ScorciatoiaAzione
prefix+n / prefix+tNuovo workspace / nuova tab (senza chiedere il nome della tab)
prefix+ctrl+up/downWorkspace precedente / successivo
prefix+ctrl+left/rightTab precedente / successiva
prefix+shift+up/downAgent precedente / successivo
prefix+1..9Focus sull’agent N
prefix+alt+1..9Passa al workspace N

La navigazione è agent-first: i numeri saltano agli agent. Workspace e tab sono solo contenitori; quello tra cui mi sposto sono gli agent.

Integrazione con Neovim: herdr-nvim#

Senza più un layout fisso con Neovim, l’editor aveva bisogno di una nuova casa. herdr-nvim risolve il problema in due metà:

  • Un plugin herdr, installato con herdr plugin install ChmaraX/herdr-nvim, che aggiunge una sidebar Neovim a tutta altezza. prefix+e la apre e chiude: i pannelli correnti si spostano nella metà sinistra, nvim prende la destra, e chiudendola torna il layout originale. Ogni tab ha il suo nvim persistente, quindi buffer e cursore sopravvivono al toggle. prefix+o apre un fuzzy picker che parte dai file toccati più di recente dall’agent, con le statistiche del diff. Anche i percorsi dei file nell’output dell’agent diventano cliccabili e si aprono nella sidebar.
  • Un plugin Neovim (dot_config/nvim/lua/plugins/herdr-nvim.lua, semplicemente { "ChmaraX/herdr-nvim", opts = {} }) per le annotazioni: commenti righe o una selezione come in una code review, poi mandi tutti i commenti a qualsiasi agent del workspace, con file:riga e contesto git.

La parte herdr la installa uno script chezmoi, run_onchange_after_setup-herdr.sh: lancia mise install herdr, poi herdr plugin install per ogni plugin della sua lista che herdr plugin list non mostra ancora. chezmoi lo esegue al primo apply e poi solo quando lo script cambia — quindi aggiungere un plugin significa aggiungere una riga alla lista.

Lato Claude Code#

herdr riconosce Claude out of the box, ma per riprendere le sessioni serve che Claude comunichi il proprio session ID. Lo fa un hook SessionStart che esegue ~/.claude/hooks/herdr-agent-state.sh, uno script generato e mantenuto da herdr. Sia la voce dell’hook in settings.json sia lo script li scrive herdr integration install claude, che lo stesso script chezmoi lancia subito dopo i plugin — insieme a herdr --skill, che rigenera la skill di herdr per Claude Code così è sempre allineata alla versione installata.

Claude Code#

Claude Code è la CLI di Anthropic per Claude ed è una presenza fissa nel mio workflow — oggi gira nei pannelli di herdr, spesso più istanze contemporaneamente. Tutta la sua configurazione è nel repo sotto dot_claude/:

  • CLAUDE.md — istruzioni globali: fai solo quello che ti chiedo, diff minimi, chiedi prima dei comandi che modificano qualcosa, dichiara il contesto kube o il workspace Terraform prima di toccare qualsiasi cosa, mai stampare segreti.
  • settings.json — modalità permessi auto con una allowlist di comandi in sola lettura (kubectl get/describe/logs, helm template/lint, flux get/logs, shellcheck…), una richiesta di conferma su ogni git push e un hard deny sull’escalation via container. È tracciato come create_settings.json: chezmoi lo scrive solo se non esiste ancora, perché sia herdr (l’hook descritto sopra) sia Claude Code stesso (/config, “always allow” su un permesso) lo modificano dopo, e un file tracciato normalmente continuerebbe a scontrarsi con loro.
  • agents/ e skills/.

Conclusione#

Un buon setup di dotfiles è invisibile quando funziona — ti siedi davanti a una nuova macchina e sembra già casa tua. chezmoi gestisce la meccanica, mise tiene aggiornato il tooling, Fish + starship mantengono la shell veloce e informativa. Quello che è cambiato quest’anno è il baricentro: il terminale non è più organizzato attorno all’editor, ma attorno agli agent — e herdr è il pezzo che ha reso questo passaggio naturale invece che caotico.
